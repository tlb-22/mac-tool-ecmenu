# 目录组织规则

本页规定当前目录职责、文件拆分与代码归属。系统边界和源码入口见[架构总述](Main.md)。

## 从业务能力到职责

按“进程 → 业务能力 → 必要的职责分层”组织代码。同一能力的界面、交互会话、业务规则、操作协调与存储一起定位；顶层使用能够说明产品组成的名称。

- `NewFileTemplates`、`CommandMenuSettings`、`GeneralSettings` 是主应用独立能力。
- `Commands` 聚合从 Finder 发起的文件操作。共享请求、Extension 菜单规则和主应用用例采用相同能力名，具体执行职责各自保留。
- `Settings` 负责设置窗口、导航和页面装配。页面内容归其业务能力，例如模板页面归 `NewFileTemplates/Presentation`。
- `App`、`CommandRuntime`、`IPC`、`Feedback` 表达进程装配、命令运行、通信和通用反馈等跨能力职责。共享代码按实际使用者与所有权归位。

## 五种可选职责目录

| 目录 | 责任与输入 / 输出 | 本项目的例子 |
|---|---|---|
| **Domain** | 用领域类型表达有效状态、预期失败和纯规则；有效值与不可变事实 → 验证结果、计划或业务结果类型 | 模板元数据、名称规则、压缩参数、尺寸计算、批量结果类型 |
| **Application** | 协调完整业务操作的读取、规则、写入与发布时机；类型化意图 → 已完成的业务结果或明确失败 | 导入模板、提交名称修改、读取模板后创建文件、压缩批次与参数请求协调 |
| **Persistence** | 保存和恢复应用长期拥有的数据，管理存储格式、提交、缓存所有权与独立迁移；保存 / 读取请求 → 已提交状态、恢复值或存储失败 | 模板索引和内部副本、菜单配置偏好、上次确认的压缩参数 |
| **Platform** | 将业务所需的系统能力适配为明确的输入、事实、结果和失败，并拥有相关系统资源生命周期 | ImageIO 转换、剪贴板写入、文件属性修改、排他创建输出文件、NSWorkspace 打开请求 |
| **Presentation** | 呈现业务状态、接收用户意图并管理界面交互会话；状态和用户事件 → 界面、草稿及应用操作请求 | SwiftUI 页面、AppKit 控件、参数窗口、名称编辑草稿、焦点与选区 |

目录按实际责任和复杂度建立。简单能力可以保留少量文件；复杂、可独立理解或需要独立维护的职责再形成子目录。一个能力可能只需要其中几类；Controller、Session、Handler 等已有类型名称可以继续表达具体角色。

不同模块使用不同文件；同一模块按独立职责与共同变化关系拆分。简单且紧密相关的类型可以共处一个文件，复杂或可独立理解的部分主动拆开，不以类型数量或文件长度机械拆分。

模块表达内聚的责任，可以由一个或多个文件实现；文件中的配套类型和局部步骤归属于同一责任。接口声明与系统实现可以按各自职责分文件，Swift extension 也遵循这一归属。目录与文档中的职责模块通过代码组织维持边界，Swift 编译模块由 Xcode target 决定；共享源码按 target 成员关系编译。

每个源码文件以中文文档注释说明整文件的职责及关键边界，随后保留就近的类型和成员注释。Swift 使用 `/** … */` 文件头，Python 使用模块 docstring，脚本保留 shebang 首行并在其后说明用途；资源与生成格式由所属目录的文档说明。

这五类用于能力内部的职责划分。设置外壳、IPC、命令运行时、通用反馈和共享契约继续使用各自明确的目录。

## 归属判断

### 业务模型与存储格式

领域模型表达业务含义和有效状态，存储索引的版本、编码结构与迁移归 `Persistence`。跨进程请求和共享值由 `ECMenuShared/Contracts` 持有，双方使用同一契约定义。按模型的语义与所有者定位代码，而不是按 struct、class 或文件后缀归类。

### Application 与 App

`Application` 表达能力内的业务操作。例如模板导入协调“读取来源 → 验证并准备副本 → 提交索引 → 发布结果”。

顶层 `App` 负责进程入口、生命周期与依赖装配，例如创建唯一模板库、连接设置页与 IPC 的读取边界。两者分别回答“怎样完成一次操作”和“进程如何构成并运行”。

### Persistence 与 Platform

按系统调用承担的业务责任归类：

| 操作 | 归属 | 理由 |
|---|---|---|
| 保存模板索引和内部文件副本 | `NewFileTemplates/Persistence` | 维护应用拥有的长期数据及其提交一致性 |
| 将上次确认的压缩参数写入偏好 | `Commands/ImageCompression/Persistence` | 恢复后续业务会话使用的设置 |
| 在用户目录生成 TXT 或压缩图片 | 对应命令的 `Platform`，简单时为能力内的系统写入文件 | 这是命令的主要业务输出，结果归用户文件系统 |
| 调用 ImageIO 或写剪贴板 | 对应命令的 `Platform` | 适配完成业务操作所需的系统能力 |

模板存储专用的文件 API 可以直接留在 `Persistence`。只有存在独立职责或真实复用需要时，才提取更低层的文件适配器。文件能长期存在，本身不足以决定代码应归 `Persistence`。

### Presentation 与 Application

名称输入、焦点、选区、输入法状态以及提交期间的控件冻结，属于模板的 `Presentation`。名称合法性由 `Domain` 决定；提交修改、读取提交结果及触发菜单更新由 `Application` 协调，索引写入由 `Persistence` 完成。

界面草稿与已提交数据各有所有者和生命周期。判断一次 Task 或 Session 的归属时，看它协调的是控件交互还是业务操作；使用异步代码或 `MainActor` 本身不决定目录。

### 依赖与系统调用

领域规则接收不可变事实并执行本地计算，可以使用 Foundation 值类型。呈现通过应用操作提交业务意图；应用操作调用窄接口或注入闭包取得持久化与系统能力；生产实现由应用装配连接。

SwiftUI / AppKit 的控件、窗口和文件选择交互属于呈现责任。SDK 名称本身不决定归属：AppKit 绘制输入框、NSOpenPanel 收集文件选择在 `Presentation`，NSWorkspace 执行业务打开请求在对应能力的 `Platform`。主要业务效果完成后，再把结果交给反馈策略。

窄接口靠近使用它的能力定义，实现按责任放入 `Persistence` 或 `Platform`；已有闭包结构可以继续使用。是否引入协议，取决于真实的调用边界、替换需要和独立实现。

## 修改界面时的查找入口

界面入口按其业务责任定位：

| 界面内容 | 查找位置 |
|---|---|
| 设置窗口、侧边栏、页面切换 | `ECMenu/Settings/` |
| 登录项与系统状态页面 | `ECMenu/GeneralSettings/Presentation/` |
| 菜单开关页面 | `ECMenu/CommandMenuSettings/Presentation/` |
| 模板列表、名称输入框、模板操作按钮 | `ECMenu/NewFileTemplates/Presentation/` |
| 图片压缩参数窗口 | `ECMenu/Commands/ImageCompression/Presentation/` |
| 通用警告窗口、进度窗口 | `ECMenu/Feedback/` |
| Finder 菜单的通用构建、布局和渲染 | `ECMenuFinderExtension/Menu/` |
| 某个命令贡献的菜单内容与可用条件 | `ECMenuFinderExtension/Commands/<能力>/` |

页面在哪里显示，由设置外壳负责；页面实现属于哪个目录，由它呈现的业务能力决定。

独立页面、窗口与弹窗的源码及预览入口见[核心界面入口](../ViewCatalog.md)。
