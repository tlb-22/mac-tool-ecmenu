# Technical spec 编写约束

本规则定义业务能力、平台专题与运行机制的长期技术说明方式。每个业务能力维护可独立定位的 spec，当前能力入口见[功能导航](../Features/Main.md)。

## 文档覆盖与归属

每个业务能力至少有一份可独立定位的技术 spec，并由所属目录的 `Main.md` 导航。能力按业务责任划分，例如模板管理、新建文件、菜单配置和图片压缩；同一能力可以覆盖多个相关命令，例如隐藏与显示共用可见性说明。

业务能力之外，具有独立复杂性、复用价值或需要较长论证的平台能力与跨能力机制，也应形成独立 spec。成熟的当前说明长期保留在 `spec/Technical/`：

| 类型 | 说明重点 | 对应技术目录与例子 |
|---|---|---|
| 业务能力 | 从用户意图到结果的完整执行流、模块分工、数据与系统边界 | `Technical/Features/`：新建文件、模板管理、菜单配置、图片压缩 |
| 平台专题 | 平台提供的能力、约束、稳定使用方式和证据范围 | `Technical/Platform/`：Finder 上下文、文件访问、原生编辑焦点、窗口行为 |
| 运行机制 | 多能力共用的协调、进程与资源生命周期、跨模块契约 | `Technical/Runtime/`：IPC、配置同步、命令生命周期、进度与取消 |

分类按说明主题决定，既有交付、预览、测试工具等技术专题可继续保留。平台或机制 spec 维护公共结论，业务 spec 说明本能力怎样使用它，并链接相应章节。

## 推荐阅读顺序与必需内容

能力 spec 在简短说明范围后，先呈现执行流，再展开模块映射、数据与 API 契约，最后给出验证证据。以下信息应当能够从该能力入口找到，篇幅与章节拆分按实际复杂度决定。

| 顺序 | 内容 | 需要回答的问题 |
|---|---|---|
| 1 | 能力范围 | 负责什么、由什么触发、与哪些能力协作？产品行为与验收边界链接哪份 Requirements？ |
| 2 | 执行流图 | 输入如何经过模块形成结果？进程、异步交接、系统调用、关键失败路径与完成点在哪里？ |
| 3 | 模块与源码映射 | 图中的每个模块承担什么职责，接收和产生什么，对应哪些目录或源码入口？修改某部分应去哪里？ |
| 4 | 数据与状态归属 | 谁拥有持久化数据、缓存、副本、草稿和任务？如何读取、更新、提交和释放？哪些状态由其他事实推导？ |
| 5 | 外部 API 与契约 | 实际使用哪些 API，输入与输出是什么，项目如何消费结果？有哪些失败、权限、线程和生命周期约束？ |
| 6 | 关键设计依据 | 哪些选择有需要长期保留的理由，哪些约束会影响后续修改？ |
| 7 | 验证与实机证据 | 自动化覆盖什么、实机怎样验证、观察到什么、适用范围与尚未验证部分是什么？ |

平台与运行机制 spec 沿用“范围与能力边界 → 使用流程 → 责任与契约 → 设计依据 → 证据”的顺序。按主题选用系统交互图、时序图、活动图或状态图，说明其调用者、适配边界和资源所有权。

## 流程图与模块映射

图应便于人类阅读，可用 Mermaid 表达借鉴 C4 的系统边界图、UML 时序图和带职责分区的活动图。先以内聚模块表达整体关系，复杂的局部流程再另图展开。

- 明确标注主应用、Extension、外部应用等进程边界；进程内 SDK 对象、系统服务和存储位置分别说明。
- 箭头标出关键输入、输出或事件，区分调用、返回、异步通知和查询响应。
- 标明会影响结果的读取、提交、写入、取消和部分成功边界。存在异步执行时，明确谁继续执行、谁等待结果。
- 对每个重要完成点说明其含义，例如命令已写出、索引已提交、文件已生成、系统接受打开请求。
- 图中的每个职责模块在邻接说明或表格中映射到代码位置，并列出职责、输入、输出及相关状态所有权。图和表使用一致的模块名称。

技术 spec 保存跨文件的执行流、模块协作、数据所有权和系统边界。函数内部步骤、完整类型定义和可直接从源码理解的局部算法由源码与测试表达；文档通过稳定入口链接到它们。

## API 与输入输出分析

每个流程都需能定位到所用外部 API 的分析。可以在模块表中直接说明，也可以用编号链接到同页 API 表或公共专题；没有外部 I/O 的模块明确标为纯规则或内存转换。

API 分析至少包含：

- **调用者与能力**：哪个模块调用、用于完成什么，以及实际使用的框架与 API 名称。
- **输入**：进入系统边界的值、重要选项和前置条件；必要时注明路径、单位、格式、权限或资源状态。
- **输出与消费方式**：API 返回值、回调或事件，以及项目实际使用了什么；区分 nil、Bool、Void、错误与业务结果的含义。
- **副作用与失败**：改变什么状态，什么时刻生效，失败后哪些变化已经发生，如何反馈或继续执行。
- **适用约束**：与该流程有关的线程、actor、资源生命周期、取消、并发、重试和可靠到达限制。
- **证据来源**：关键官方契约链接、项目技术结论或实测证据；明确哪些是由这些材料推导的设计判断。

输入输出分析围绕实际使用方式展开。每个 SDK 的全部参数和所有普通视图修饰符不作机械枚举；异步通知、系统接受请求或无返回值的调用，也不能据此推定业务已完成。

## 验证与实机证据

自动化与实机验证分别说明。存在测试定义只表示已有验证入口，执行通过记录需要对应的实际运行证据；自动化覆盖范围与真实系统交互的验收范围应当清楚区分。

实机结论保留可复现的关键条件：项目版本或源码基线、macOS 与相关工具版本、必要环境状态、操作方法、实际观察、失败表现，以及结论的适用范围。证据明确区分：

- **官方契约**：平台文档或 SDK 声明承诺的行为。
- **项目观察**：指定环境与样本中实际发生的行为。
- **推断与设计判断**：从契约或观察得到的解释及其证据限制。

实机部分沉淀稳定使用路径、关键失败路径及原因，不按尝试时间顺序记录流水账。尚未验证的边界明确标注；纯规则等无需独立实机验证的内容说明相应自动化依据即可。

需要复现的测试与诊断入口链接 `Tests/` 或 `scripts/`。临时运行产物遵守项目产物目录规则；长期结论写入 spec，临时日志或截图不作为唯一证据载体。

## 渐进展开与维护

简单能力可以使用一份短文档。复杂能力按高内聚职责拆成目录，`Main.md` 只保留总述、关键结论和导航；阅读路径先引导到流程图，再进入相应细节。具体章节数量由主题需要决定。

同一公共结论有一个权威维护位置。业务 spec 保留本能力的调用输入、结果解释与特定约束，并引用公共机制；产品行为与验收要求由 `Requirements` 维护。

行为、模块边界、状态所有权、API 用法或证据范围变化时，同步更新关联流程、模块映射与技术约束。仅调整目录或文件位置时，更新源码入口与导航；被替代的重复内容及时删除。

`Technical` 陈述当前成立的技术事实与设计依据。文档面向未参与讨论的读者，从最终成立的方案重新组织正文。
