## 关键结论

- 两个产品进程的边界已经清楚：Finder Extension 构建菜单并投递命令；主应用管理配置、模板、文件操作和反馈。保留这一分工。
- 主要改进对象是能力内部的组织：模板管理跨越设置页和模板目录；部分命令把模型、执行、系统适配与反馈放在同一文件；生命周期装配依赖静态共享对象。
- 建议采用“**进程 → 业务能力 → 必要的职责分层**”。界面负责呈现与编辑会话，用例负责协调，领域类型负责有效输入和结果，平台适配器负责外部 I/O。
- 首要语义调整是明确业务完成点、模板变更提交结果和配置发布责任。目录应反映这些责任，随后再移动文件。

## 图的阅读方法

采用 Mermaid 表达借鉴 C4 的系统边界图、UML 时序图和带职责分区的活动图；使用精简记法，便于阅读和随源码一起审阅。

- **系统图**中的大框表示进程或系统；小框表示职责模块。`ECMenuShared` 是编译进两个产品的代码，不是第三个进程。
- **时序图**从上到下阅读，生命线按职责排列，`box` 标出进程或明确命名的系统 API / 存储边界。AppKit、Foundation、ImageIO 等 SDK 对象仍在调用进程内，不另算进程；实线箭头表示调用/消息，虚线箭头表示返回值或完成回调；编号只表示图中的顺序。
- **活动图**用职责分区组织步骤，菱形表示会改变路径的条件，圆柱表示持久化存储；标为通知的箭头不代表确认。
- 图上保留关键数据与 API 名；邻接表说明完整的输入、输出、实际使用的返回值及失败。模块没有外部 I/O 时明确注明。
- “成功”必须说明完成的层次：系统接受打开请求、socket 已写出、索引已提交、文件已生成和用户已看到结果具有不同含义。

“外部 API”包括 Apple SDK、Darwin/POSIX 和开发工具命令行边界；项目自身的 Controller、Handler、Repository 是内部契约。纯算法和普通视图修饰符不逐个罗列。[API 证据说明](APIContracts.md)给出关键官方来源和解释限制。
