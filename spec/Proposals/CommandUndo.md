# 命令撤销与重做【待决策】

本提案不属于当前产品行为和验收范围。目标是在 Finder 工作流中恢复 ECMenu 对文件造成的变化；平台能力与证据限制见 [Finder 撤销集成边界](../Technical/Platform/Finder/UndoIntegration.md)。

## 范围与入口

撤销的价值集中在可逆的文件变更。建议范围如下：

| 命令 | 撤销 | 重做 |
|---|---|---|
| 新建 TXT | 从原位置撤回本次创建且状态符合预期的文件，保留恢复资源 | 恢复同一产物 |
| 隐藏 / 显示 | 恢复每个实际改变对象执行前的隐藏属性 | 恢复这次操作写入的属性 |
| 压缩图片 | 撤回该批实际生成且状态符合预期的 JPG，保留源图片与恢复资源 | 恢复同一批产物 |

拷贝路径不进入文件历史：恢复剪贴板需要独立的多格式快照与所有权语义，并可能影响用户后续复制。进入 VS Code / iTerm2 也不进入历史：ECMenu 只拥有系统打开请求，不拥有外部应用中随后产生的窗口、编辑或任务状态。

Finder 原生 ⌘Z / ⇧⌘Z 与 ECMenu 自有撤销是两种不同的产品边界。建议先验证原生文件操作的间接集成；自有历史路线可提供 Finder 上下文菜单中的“撤销 ECMenu 操作”和“重做 ECMenu 操作”，快捷键采用独立入口并另行验证。自有入口不宣称与 Finder 原生操作混合排序。

## 历史语义

- 一次用户命令是一个撤销单位，只记录实际完成的变更。纯失败、没有变化、取消参数窗口不产生条目。
- 批量部分成功以及中途取消保留下来的产物形成一个条目；取消不抹去已经发生的文件变化。
- 隐藏或显示混合状态对象时，分别记录每个对象的原状态。已处于目标状态的对象不生成逆操作。
- 重做恢复已产生的文件及其实际属性，不重新读取源图片、重新编码或弹出参数窗口。
- 新的有效文件变更在历史顺序边界上结束旧的重做分支；失败或无变化不会无故清空重做。
- 第一版候选范围为主应用本次进程会话；状态页关闭不结束历史，主应用退出或重启结束历史。跨启动恢复需要独立的持久化与迁移设计。

## 文件冲突与恢复资源

路径不能单独充当文件身份。记录要关联执行时的对象身份和操作相关的预期状态；具体身份与存储适配器需验证符号链接、同卷/跨卷以及支持的文件系统行为。

撤销前目标已被编辑、替换、删除或移动，以及重做时原位置已被占用、卷离线、权限改变，都是实际可能发生的运行时失败。无法确认仍为预期对象时停止该项并说明冲突，保留当前内容，不按旧路径删除或覆盖其他文件。仅检查时间戳或先检查路径再写入不足以消除竞态。

撤回产物必须先具有可恢复的存储安排。恢复存储的容量、清理时机、外置卷支持和进程异常结束后的残留处置是文件功能接入前的验收项；运行时存储由应用管理，不依赖仓库 scratch 或 Derived Data。

部分撤销失败时，结果分别保存已经撤销的变更和仍然生效的变更。历史只能按实际结果迁移；不能把整条记录标记为成功或丢弃未完成部分。进入下一次历史操作前应明确呈现可重试/冲突状态。

## 实施步骤

### 1. 原生能力验证

在独立测试账户或可丢弃的测试环境中建立 fixture。先比较 Finder UI 与 Finder Apple Events 复制单个、一批准备好的文件到目标目录的结果，再验证原生撤销和重做；`NSWorkspace.duplicate` 的同目录复制作为另一项独立对照。最低支持的 macOS 26.0 与当前验证版本均需验收，分别检查：

- Finder 编辑菜单的动作名称、启用状态与一次按键的分组。
- 与 Finder 原生移动、重命名交错执行后的顺序。
- 批量部分失败、重名、跨卷、Finder 重启以及重做时准备文件不再存在的结果。
- 从实际签名的 ECMenu Debug 主应用调用时的自动化授权、拒绝、取消与系统 UI。

验证代码维护在 `Tests/` 或 `scripts/`；一次性日志和 fixture 按仓库规范放在 `.artifacts/scratch/`。实验不把工作会话中既有 Finder 历史当作可恢复状态。

只有具体操作满足对应产品行为时，才为该操作采用 Finder 代执行。若要求全部命令进入 Finder 原生历史，则此阶段为可行性门槛；当前公开接口审阅不能承诺通过。

### 2. 自有历史核心

若采用 ECMenu 自有历史，主应用是历史与恢复资源的唯一所有者，在 `ECMenu/ContextCommands/History/` 形成能力边界。使用创建产物、可见性变化、历史条目身份、操作方向和失败原因等领域类型；历史保存执行事实，菜单可用性由历史推导。

历史登记位于文件副作用完成后的执行边界，与 UI 呈现分离。当前执行框架在 Task 取消后会跳过 `present`，因此不能把成功变化的登记挂在该出口。

保留参数等待和图片编码的并发能力，为受历史管理的文件提交、撤销、重做建立明确的顺序，并协调同一对象的写入。不能让同一批变化交错写入后只按批次结束时间排序；实际副作用顺序必须与历史顺序一致。

### 3. 功能接入与 Finder 入口

先接入只改变属性的隐藏/显示，再接入需要保存恢复产物的新建 TXT 与图片压缩。每个 Handler 返回实际成功变更凭据，错误与部分成功遵循统一结果模型。

共享 IPC 增加历史查询和撤销/重做请求。Extension 只持有主应用提供的历史摘要；菜单点击绑定条目 ID 与历史修订号，过期请求返回明确失败，避免菜单展示后栈顶变化而撤销了另一项。业务完成必须由主应用确认，不能以请求发出成功推断历史变化。

### 4. 验收

测试重点是混合隐藏状态、已编辑产物、同路径替换、恢复位置冲突、符号链接、部分成功、执行后取消、连续撤销/重做、重做分支失效、同对象并发、旧菜单请求和进程生命周期。文件适配器补充真实文件系统集成测试。

按仓库入口运行 `./scripts/test.sh`。修改 Extension 后使用 `./scripts/run-debug.sh --refresh-finder`，确认当前 Debug 登记与进程后验收真实 Finder 菜单。

采用后把确定的产品行为迁入 Requirements，把实测平台结论补入 Technical，并同步运行时、IPC 与功能文档。
